> 阶段目标：把一段口语化的产品设想，还原成**可评审的问题域定义**。本文件不做加工，只做「去重、拆解、标注假设、列出待确认项」。后续所有 Requirements 与 Design 都必须能追溯到这里的某一行。

## 0.1 原始输入（逐条拆解，保留原意）

| # | 原始表述 | 拆解出的意图 |
|---|---|---|
| P-01 | 可嵌入在企业的报表系统里 | 宿主是已有企业系统，本平台以「嵌入式 / 独立部署 + iframe 集成」形态存在 |
| P-02 | 可以通过提示词生成 SQL | 自然语言 → SQL（NL2SQL）是核心能力，不是辅助能力 |
| P-03 | 直接生成报表并导出，有 preview 功能 | 生成后必须先看（Preview），再决定产出；导出是一等公民 |
| P-04 | 确认后用户可决定是否保存为常用报表，或只是临时的一个导出数据 | 收敛路径有二：① 保存为常用报表（持久化）② 临时导出（不落报表）；二选一，确认动作是分叉点 |
| P-05 | 基本上 80% 都是这种情况 | 「临时导出」是主路径，约 80%；常用报表约 20%（容量与交互权重据此倾斜） |
| P-06 | 当企业用户无法用提示词生成需要的报表，通过平台和我们开发者协作 | 存在一条「人机协作降级通道」：甲方提需求 → 开发者介入 |
| P-07 | 由开发者修改 SQL 实时生成报表由企业用户确认 | 开发者改 SQL 后甲方**立即可见**（无发布/重启环节）；甲方有确认权 |
| P-08 | 删除的报表对甲方不可见，对开发者超管仍存在，只是状态是删除 | 删除是**软删除**，且是**按角色分层**的软删除 |
| P-09 | 分两种角色：开发者和甲方 | 角色模型只有两个，无 RBAC 权限矩阵 |
| P-10 | 选择开发者角色，可以配置数据库链接 | 数据源配置是开发者独占能力 |
| P-11 | 选择甲方，直接看到配置好的报表 | 甲方是「消费侧」，开箱即用，零配置 |
| P-12 | 甲方和开发者都无需登录，直接可打开报表管理后台 | **无认证**。访问入口即身份 |
| P-13 | 根据域名和目录区别不同的 web 应用报表 | 多应用隔离维度 = 域名 + 目录前缀 |
| P-14 | 开发者的编辑查询 SQL 需防止安全问题 | SQL 注入/越权/破坏性语句/凭据泄露是首要风险 |
| P-15 | 有类似标签管理器的工具 | 需要一棵可自定义的目录/标签树来组织报表 |
| P-16 | 默认配置好的报表在根路径下，用户可定制放在指定目录下 | 默认挂载在根，支持移动到自建目录 |
| P-17 | 甲方删除 → 放进「回收站」文件夹，不显示在左侧菜单；可放回原处；可清空 | 回收站三动作：删除（入站）、还原（回原位）、清空（不可逆地对该角色消失） |
| P-18 | 清空后甲方看不到，但开发者仍然能看到该报表 | 甲方「清空」≠ 物理删除，只是甲方侧 PURGED |
| P-19 | 开发者有同样的回收站功能，但在回收站里清空 = 彻底删除 | 开发者「清空」= 物理删除（hard delete） |
| P-20 | 开发者和甲方拥有同样的所有报表，但可以有各自组织的标签结构 | 报表全集相同；但**每个角色有一棵独立的标签树** |
| P-21 | 每个报表记录甲方的需求、开发者的 SQL 并可查看 | 报表 = 需求 + SQL 的载体，有留痕 |
| P-22 | 甲方能查看自己对该报表的需求；开发者可完整查看甲方的需求、开发者的 SQL | 需求/SQL 的**可见性按角色分级**：甲方看不到 SQL |

## 0.2 问题域一句话定义

> 面向企业内部、**免登录**的轻量报表平台：以「提示词生成 SQL → 预览 → 导出或沉淀为常用报表」为主路径，提供「甲方提需求 / 开发者改 SQL」的协作降级通道，并通过**每个角色独立的标签树**与**双层回收站**管理报表的按角色生命周期。

## 0.3 关键假设（Assumption）

> 凡本轮未确认者，均按下列假设推进；假设一旦不成立，对应需求需回炉。

| ID | 主题 | 假设 | 若不成立的影响 |
|---|---|---|---|
| A-01 | 部署形态 | 一期为独立 Web 应用，可 iframe 嵌入宿主系统；不做统一门户 | 涉及 SSO 与菜单集成方案重做 |
| A-02 | 认证 | ✅**已确认**（Q-01）完全无登录；安全性由「网络边界 + 只读账号 + 审计 + 发布检查清单」补偿 | 若公网部署，必须在网关层加 SSO/IP 白名单 |
| A-03 | 角色判定 | 同一域名/应用下，通过**不同目录前缀**进入不同角色（如 `/{app}/c/` 与 `/{app}/d/`） | 需改为角色选择页或首次访问记忆 |
| A-04 | 身份标识 | 无登录即无用户实体；操作留痕以「角色 + 匿名客户端标识（本地生成的 clientKey）」记录 | 审计粒度下降，问责困难 |
| A-05 | 数据源 | ✅**已确认**（用户决策）一期仅 MySQL；连接层做适配器抽象，预留 PostgreSQL / ClickHouse | 需扩展方言改写与元数据抓取 |
| A-06 | 数据源权限 | 所有业务库连接强制使用**只读账号**，由运维侧授予 | 平台侧需额外做账号权限校验 |
| A-07 | SQL 能力边界 | 仅支持只读查询（SELECT / CTE），不支持存储过程、临时表、跨库 JOIN | 复杂报表需走视图或数仓预建 |
| A-08 | NL2SQL 输入 | 仅把**库表结构元数据 + 用户提示词**发给大模型，不发送业务明细数据 | 涉及数据出境/外泄合规 |
| A-09 | 报表归属 | 报表属于「应用」，不属于个人；两角色看到同一全集 | — |
| A-10 | 临时导出产物 | ✅**已确认**（Q-04/Q-09）导出文件 TTL 24h，异步任务记录保留 72h，另提供 30 天「我的导出历史」 | 需长期归档则要加文件管理模块 |
| A-11 | 用量规模 | 单应用并发 SQL ≤ 5，单次返回上限 5 万行，超时 30s | 需引入异步查询队列 |
| A-12 | 需求协作 | ✅**已确认**一期为异步协作（提交 → 开发者处理 → 甲方确认），不做在线协同编辑 | — |

## 0.4 术语表（Glossary）

| 术语 | 英文/代号 | 定义 |
|---|---|---|
| 应用 | Application | 由「域名 + 目录前缀」唯一标识的一个隔离空间，拥有独立的数据源、报表、标签树 |
| 角色 | Role | 仅两个取值：`DEVELOPER`（开发者/超管）、`CLIENT`（甲方/企业用户） |
| 甲方 | Client | 消费报表的企业用户；可提需求、生成 SQL、预览、导出、保存、组织目录 |
| 开发者 | Developer | 配置数据源、编写与修改 SQL、处理需求、拥有最终删除权 |
| 报表 | Report | 一条可复用的查询定义，承载 SQL、需求、参数与生命周期状态 |
| 常用报表 | Saved Report | 已持久化的报表，出现在标签树与左侧菜单 |
| 临时导出 | Ad-hoc Export | 未创建报表记录的一次性查询导出（主路径，约 80%） |
| 预览 | Preview | 以受限行数（默认 200 行）执行 SQL 并展示列结构与样例数据 |
| 标签管理器 | Tag Tree | 每角色每应用一棵的目录树，用于组织报表；含一个内置的回收站节点 |
| 标签/目录节点 | Tag Node | 树中的一个节点；根节点与回收站节点为系统内置 |
| 回收站 | Recycle Bin | 每棵树下内置的不可删除节点，承载该角色 `RECYCLED` 状态的报表 |
| 清空 | Purge | 甲方侧＝对甲方永久不可见；开发者侧＝物理删除记录 |
| 生命周期 | Lifecycle | 报表在某个角色视角下的可见状态：`NORMAL` / `RECYCLED` / `PURGED` |
| 需求 | Requirement | 甲方针对报表提出的自然语言诉求，可多轮追加 |
| SQL 版本 | SQL Version | 报表 SQL 的每次变更留痕，含作者、时间、前值 |
| 数据源 | DataSource | 一个只读数据库连接配置（一期 MySQL） |
| 元数据目录 | Catalog | 数据源的库/表/字段/注释结构缓存，供 NL2SQL 使用 |

## 0.5 范围界定

**In Scope（本轮）**
- 双角色与免登录访问；应用级（域名+目录）隔离
- **平台根应用**与其他应用的创建/停用（Q-08）
- 数据源配置（开发者）与元数据抓取
- NL2SQL → 安全校验 → 预览 → 导出 / 保存为常用报表
- **报表参数（占位符 + 参数绑定执行）**（Q-03）
- **我的导出历史**（Q-09）
- 甲方提需求 → 开发者改 SQL → 甲方确认 的协作闭环
- 每角色独立标签树 + 回收站（还原 / 清空）
- 双层生命周期、宽限期与开发者物理删除（Q-06）
- 需求与 SQL 的留痕与按角色可见性（Q-02）
- SQL 执行安全、凭据保护、审计日志
- 无边框嵌入模式与 postMessage 高度自适应（Q-10）

**Out of Scope（明确不做，后续轮次）**
- 登录/权限矩阵/用户体系/组织架构
- 图表可视化（柱状/折线/透视）、仪表盘编排
- 定时调度、订阅推送、报表快照
- 多数据源联合查询、跨库 JOIN、存储过程
- 行级权限（不同甲方看不同数据行）
- 报表的版本回滚 UI（数据已留痕，UI 后续补）
- 移动端适配

## 0.6 决策收敛记录（原 Open Questions）

> **状态：Q-01 ~ Q-10 已于 2026-10-02 全部收敛**，完整结论、依据与被否掉的备选见 `03-decisions.md`。
> 收敛时新暴露的次级问题（Q-11 ~ Q-15）不影响 S1 启动。

| ID | 问题 | 影响面 | **结论** |
|---|---|---|---|
| Q-01 | 免登录部署在公网是否可接受？ | SEC / 架构 | **平台不实现认证**；发布检查清单强制二选一：内网部署 或 网关层 SSO/IP 白名单 |
| Q-02 | 甲方是否需要看到 SQL？ | META / 交互 | **应用级开关 `clientCanViewSql`，默认 false**；开启后甲方只读可见当前生效 SQL |
| Q-03 | 报表是否需要参数？ | 数据模型 / NL2SQL | **一期实现**：`{{name}}` 占位 + 类型定义 + **强制参数绑定执行** |
| Q-04 | 导出格式与上限？ | EXP | **xlsx + csv**；同步上限 5 万行/30 秒，超限转异步；文件 TTL 24h，任务记录 72h |
| Q-05 | 甲方清空后是否允许开发者代恢复？ | LIFE | **允许，但只恢复到甲方回收站（`RECYCLED`）**，是否放回菜单由甲方决定 |
| Q-06 | 开发者清空是否需要宽限期？ | LIFE / 运维 | **默认 7 天，可配 0~30**；`0` 为立即物理删除；宽限期内可撤销 |
| Q-07 | NL2SQL 使用哪家模型？ | 合规 / 成本 | **应用级配置 endpoint/model/apiKey**，默认指向私有化或合规审批接口；出站仅「元数据+提示词」 |
| Q-08 | 谁来创建一个「应用」？ | 治理 | **内置平台根应用**（`is_platform_root`），其开发者可创建/停用其他应用；**不引入第三角色** |
| Q-09 | 临时导出是否留痕？ | EXP / 审计 | **进审计日志**，并新增「我的导出历史」（当前 clientKey，30 天，支持过期重跑） |
| Q-10 | iframe 嵌入的跨域问题？ | 接入层 | **无边框模式 + postMessage 高度自适应**；建议宿主反向代理挂同域子路径 |
