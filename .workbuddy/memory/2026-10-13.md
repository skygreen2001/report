# 2026-10-13 企业报表平台

## 多用户隔离方案再修订（讨论阶段，待用户确认后实施）

**上一版为什么没达到效果**（已定位）：用 URL 里的 `ws` key 区分人，但实际使用中大家都直接打开 `/d`（不带 key），
于是全部落进同一个「默认工作区」→ 看起来还是共享的。教训：**身份不能依赖人手动在 URL 里带 key**。

**用户提出**：把开发者的数据源配置放在浏览器本地（localStorage），报表存数据库。

**我的技术判断（已回复用户）**：方向对（用浏览器天然隔离身份），但**数据源不能纯放浏览器本地**，两个硬伤：
1. 报表在数据库里共享，别人在 `/c` 打开该报表时，**服务器**要连库执行 SQL，需要数据源主机/账号/密码；
   只存在浏览器里服务器拿不到 → 报表"看得见名字、点开报错"。
2. 数据源含数据库密码，localStorage 是明文；清缓存/换设备即丢。

**推荐方案（待确认）**：身份放浏览器、配置仍放服务器。
- 浏览器本地只存**随机身份 ID**（无敏感信息，localStorage 或 httpOnly cookie），首次访问自动生成。
- 数据源 / 模型 / 目录**仍存服务器**，按该身份 ID 归属与隔离（别人查不到）。
- 报表存数据库且**共享**；执行时服务器用报表绑定的 data_source 连库，不受"当前是谁"限制。
- 效果：不同浏览器天然隔离（不用发链接、菜单不变）；`/c` 看所有人的报表且能跑；人人既是开发者也是甲方。
- 代价：换设备/清缓存丢身份（可加"导出/导入身份"或保留 `?ws=` 作为备份入口）。

**待用户拍板后实施**：改 `resolveWorkspace` 为 per-browser 身份 + 存量数据迁移到新身份维度。

## ✅ 已实施：浏览器身份模型（用户回复"开干"后完成并验证）

**最终架构**：身份放浏览器（Cookie）、配置放服务器、报表共享。人人平等，菜单零改动。

**改动清单**：
- `middleware.ts`：`?ws=` 参数 > `wsKey` Cookie > **现场生成 18 位 hex 并写 Cookie**（d 和 c 都处理）。
  生成时额外置 `x-ws-generated: 1` 头。首次访问即拥有身份，无需登录、无需发链接。
- `context.ts`：新增 `readWsGenerated(req)`；`resolveWorkspace(appId, wsKey, generated)`。
- `devWorkspace.ts` `resolveWorkspace` 逻辑：
  1. key 已存在 → 直接返回（同浏览器换页面仍是同一套）。
  2. 新 key 且 `generated=true` → **认领**本应用 `claimed=0` 的最早工作区（存量配置不丢）。
  3. 新 key 但来自 `?ws=` 链接 → **只新建**，绝不抢占别人的存量配置（防手搓链接偷配置）。
  4. 非法格式 key → 404。
- `schema.sql` / `dev_workspace` 新增 `claimed TINYINT(1) DEFAULT 0`（0=待认领，被访问即置 1 并绑定 ws_key）。
- `types.ts` `DevWorkspaceRow` 加 `claimed`。
- 迁移 `scripts/migrate-ws-browser-identity.ts`（幂等）：加列 + 全部存量置 `claimed=0`。
  （更早的 `migrate-ws-flatten.ts` 负责去掉 OWNER 层级，已执行。）

**验证（live 3111，两个 cookie jar 模拟两个浏览器）**：
| 场景 | 结果 |
|---|---|
| 浏览器 A 首次进 `/d` | 认领存量「主开发者」，看到业务只读库 + 1 张报表（老配置没丢）|
| 浏览器 B 首次进 `/d` | 全新空工作区（数据源 0、报表 0）—— 私密，需自己配 |
| A / B 再次进 `/d` | 各自稳定停在自己的工作区 |
| B 打开 `/c` | 看到全部报表（1 条，标注"来自：主开发者"）|
| 手搓 `?ws=aaaabbbbccccddddee` | 只新建工作区，存量 3 个 `主开发者` 仍 `claimed=0` ✓ |

tsc 0 错误；网关对抗 20/20；生命周期 38/38；`/demo/d`、`/demo/c`、`/platform/d`、`/platform/c` 均 200。

**⚠ 运维要点（重要）**：
- 「第一个打开页面的浏览器」会认领该应用待认领的工作区。所以**联调测试后必须复位**
  （`UPDATE dev_workspace SET claimed=0` + 换 key），否则用户自己的浏览器会拿到空工作区、看不到老配置。
  测试期间我用过一次性脚本 `scripts/tmp-ws-reset.ts`（用完已删），必要时可照此重写。
- 当前状态已复位：demo / platform / bb 三个应用的「主开发者」均为 `claimed=0`，等用户浏览器认领。
- 页面（`/d`、`/c`）本身不会触发认领——只有 `/api/*` 调用才会 `resolveWorkspace`。
- 换设备/清缓存会丢身份；恢复方式是保留 `?ws=<key>` 链接（需从库里取 `dev_workspace.ws_key`）。
