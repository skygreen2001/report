## 修复：应用管理「停用」点了没反应

**根因**：`d/page.tsx` 调的是 `${api}/applications/${id}:disable`（冒号式动作路径），而真实路由是 `applications/[id]/disable/route.ts`（斜杠式）。冒号路径 Next 匹配不到 → 404；前端 `await r.json()` 在 404 的非 JSON 响应上抛异常，又没有 try/catch → 错误被吞掉，页面零反馈 = 「没反应」。

（同类坑之前也踩过：`/reports/{id}:delete` 405，正确是 `/reports/{id}/delete`。前端只剩这一处冒号式调用了，已全清。）

**改动**
- `d/page.tsx`：`disableApp` 换成 `setAppStatus(a, 'DISABLED'|'ACTIVE')` —— 路径改 `${api}/applications/${id}/disable|enable`；加 `confirm()` 二次确认；`r.json().catch(() => ({}))` 兜底 + try/catch，失败一定弹得出提示（含 HTTP 状态码）。
- 应用列表显示状态：平台根打「平台根」徽标，`status==='DISABLED'` 打「已停用」并给「启用」按钮，停用中的不再显示停用按钮。
- 新增 `src/app/tenant/[appPath]/[role]/api/applications/[id]/enable/route.ts` + `application.ts` 的 `enableApplication()`：停用可逆（原来误点一次只能手工改库）。

**验证（live）**：旧 `:disable` 路径 404 → 新 `/disable` 200 且 status 变 DISABLED → 停用后访问 `/tmp-disable/c/api/bootstrap` 404（缓存即时失效生效）→ `/enable` 200 恢复 ACTIVE。回归：生命周期 38/38、Web E2E 15/15。临时应用与两条 `生命周期验证-*` 脚本残留应用已清理，库里剩 demo / bb / platform 三个。

## ★ 环境坑：dev 服务启动必须去掉 NODE_OPTIONS

**现象**：dev 服务（3111）某次重启后全站 500，日志刷 `EEXIST ... mkdir '.next' / CODEBUDDY_BROKER_DENY`，`webpack.cache.PackFileCacheStrategy Caching failed`。

**根因**：环境注入了 `NODE_OPTIONS=--require .../node-language-shim.cjs`，该 shim 对文件操作有「每回合 50 次」的限流（和 safe-delete 的 `count:50 threshold:50 scope:turn` 同源）。全量编译 .next 要写成千上万个文件 → 触发限流 → mkdir 被 deny → 编译产物写不进 → 500。服务已编译好、只有少量热更新时不会触发，所以间歇性出现。

**解法（记牢）**：
```bash
cd report-platform
env -u NODE_OPTIONS /Users/skygreen/.workbuddy/binaries/node/versions/22.12.0/bin/node \
  node_modules/next/dist/bin/next dev -p 3111
```
如果 .next 已被写坏，先 `mv .next /tmp/xxx`（移动，别删）再启。同理，跑 tsx 脚本也建议加 `env -u NODE_OPTIONS`。

**配套**：本地 tsc 用 `node node_modules/typescript/bin/tsc --noEmit`（**不要用 npx tsc**，会去装别的 tsc 包并卡死在网络）；tsx 用 `node node_modules/tsx/dist/cli.mjs`（.bin 软链不存在）。dev 服务必须用 `run_in_background` 启动（普通 `&` 会随命令结束被杀）。改完路由若出现 `__webpack_modules__[moduleId] is not a function`，说明 HMR 缓存坏了：`mv .next /tmp/xxx` 后重启即可。

## ★ 修复：重复数据源（创建去重 + 改派删除合并）

1. **创建去重**：`createDataSource` 插入前查同应用 `(host,port,database_name,username)` 完全相同 → 409 `DATA_SOURCE_DUPLICATE`，提示「该数据源已存在…请勿重复添加」。根治重复产生。

## 修复：模型配置下拉选厂商后「显示名」输入框不变

**根因**：`d/page.tsx` 与 `c/page.tsx` 的 `applyPreset(vendor)` 用 `name: f.name || (p ? p.label : f.name)`。一旦 `f.name` 非空（哪怕是上一次选预设自动填的标签），再切厂商就走旧值，名称不再跟随 → 用户看到「选了模型但名字没变」。

**修复**：改为 `name: p ? p.label : f.name` —— 选厂商预设时「显示名」始终跟随该厂商预设标签（接口地址、默认模型名本就跟随）。两文件同步改。tsc 0 错误。HMR 即生效，刷新即见。

## 修复：甲方配了本地 Ollama 但生成报表报「未配置可用模型」

**根因**：`generation.ts` 用 `if (!p || !p.endpoint || !p.apiKey)` 判「无模型」。本地/自建模型（ollama/vllm/xinference/lmstudio，以及自定义 OpenAI 兼容）本就无需 key，其 `api_key_enc` 为空。旧逻辑把空 key 误杀 → 返回 `mode:'manual'` 带「未配置可用模型（请到模型配置添加你自己的模型）」；因 `p` 非空 `noModel:false`，前端走「LLM 生成失败：」分支（非提交需求）。live 库印证：甲方 ollama `scope=CLIENT,status=ACTIVE,key=EMPTY`；开发者端 ollama 有 key 故不触发。

**修复**：`generation.ts` 拆三层——
1. `!p` → 真·无模型（noModel:true，甲方交需求给开发者）；
2. `!p.endpoint || !p.model` → 缺连接信息；
3. 仅当「云端厂商（非 local、非 custom）且缺 key」才报「缺少 API Key」；本地/自定义模型放行。客户端 apiKey 用 `|| 'EMPTY'`，与 `testProvider` 一致。
导入 `presetOf` 判断 `local`。tsc 0 错误；dev(3111)+ollama(11434) 在线，刷新即验。
