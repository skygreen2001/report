# 2026-10-15 企业报表平台

## ws_key 可见性：加查询脚本 + bootstrap 回传身份（界面零改动）

**背景**：用户问「`dev_workspace.ws_key` 在哪里，我找不到」。它不在代码里，是 MySQL 表
`report_platform.dev_workspace` 的一列，界面上看不到（上一轮按「界面不要动」的要求撤掉了徽标）。

**改动**：
- 新增常驻脚本 `scripts/ws-list.ts`（幂等只读）：列出全部工作区的 应用 / 名称 / 状态 / claimed /
  数据源数 / 报表数 / **ws_key**，并直接打印换设备用的 `/{app}/d?ws=<key>` 链接。
  运行：`env -u NODE_OPTIONS .../node node_modules/tsx/dist/cli.mjs scripts/ws-list.ts`
- `bootstrap` 接口回传 `workspace.wsKey`（只回给本人）：浏览器地址栏直接打开
  `/{app}/d/api/bootstrap` 就能看到自己的身份 key，无需连库、无需改 UI。
  → `types.ts` `RoleContext` 加 `wsKey`；`context.ts` 赋值 `wsKey: ws.ws_key`；
  → 三个 verify/smoke 脚本的 `RoleContext` 字面量同步补 `wsKey: ws.ws_key`。
- 修正 bootstrap 里一处过期注释（还写着 OWNER 层级）。

**三种查 key 的方式（给用户）**：
1. 浏览器打开 `http://127.0.0.1:3111/demo/d/api/bootstrap` → JSON 里 `workspace.wsKey`
2. `node_modules/tsx/dist/cli.mjs scripts/ws-list.ts`
3. `mysql -u root -proot report_platform -e "SELECT ws_key,name,claimed FROM dev_workspace;"`

**⚠ 运维要点（沿用 10-13 结论，本次再次踩到）**：
- 「第一个调用 `/api/*` 的浏览器」会认领该应用 `claimed=0` 的工作区，并把 ws_key **替换成自己的随机串**。
  因此联调后必须复位：`UPDATE dev_workspace SET claimed=0 WHERE app_id=...`，并删掉测试产生的新工作区
  （连同 `tag_node WHERE ws_id=...`）。
- 本次测试后已复位：demo / platform / bb 三个「主开发者」均为 `claimed=0`；
  同时清掉了一个测试遗留的空工作区，以及一个 app 早已不存在的孤儿工作区 `86b18a2c`。
- demo 工作区当前 ws_key = `641159fb284844059f`（待认领，用户浏览器接管后会再变）。

**验证**：tsc 0 错误；网关对抗 20/20；`/demo/d`、`/demo/c` 均 200；
两 cookie jar 实测：浏览器1 认领存量（数据源1/报表1，wsKey=641159fb284844059f），
浏览器2 拿到全新空空间（数据源0/报表0）。
